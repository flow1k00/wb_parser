
# WB Parser

Консольная утилита для сбора данных о товарах с Wildberries по артикулам. Экспортирует результаты в локальный Excel-файл и Google Таблицы.

Изначально проект разрабатывался для решения коммерческой задачи по сбору аналитики в условиях жестких ограничений со стороны маркетплейса на автоматический сбор данных

## Возможности

- Сбор данных (название, бренд, цена, скидка, рейтинг, количество отзывов, остаток) из двух независимых источников WB.
    
- Автоматическое переключение (fallback) между источниками при сетевых сбоях или блокировках.
    
- Обход региональных ограничений за счет перебора идентификаторов доставки.
    
- Контроль темпа запросов (randomized delays, batch pauses) для снижения нагрузки на сервер и обхода бана.
    
- Дедупликация входных данных с сохранением исходного порядка артикулов при экспорте.
    

## Архитектура и отказоустойчивость

Wildberries не предоставляет единого открытого API и применяет механизмы защиты от парсинга. Для обхода этих ограничений парсер использует двухуровневую систему сбора:

1. **Динамический Card API (`card.wb.ru`)**
    
    Основной источник актуальных данных о ценах, скидках, рейтинге и остатках. Поскольку доступность и цена зависят от геолокации покупателя, парсер последовательно опрашивает массив эндпоинтов с разными параметрами `dest` (регионы доставки) и `appType`, пока не получит успешный ответ HTTP 200.
    
2. **Статический Basket CDN (`basket-NN.wbbasket.ru`)**
    
    Резервный механизм. Включается, если Card API блокирует запрос или не возвращает данные. Карточки хранятся на множестве CDN-серверов. Парсер вычисляет нужный узел по артикулу:
    
    - Артикул делится на `100 000` для получения параметра `vol`.
        
    - По таблице соответствия определяется базовый номер сервера (от 01 до 25).
        
    - Формируется URL вида `basket-05.wbbasket.ru/vol.../part.../info/ru/card.json`.
        

**Fallback-механики:**

- **Neighbor Probing:** Распределение товаров в CDN WB периодически меняется. Если расчетный сервер не отвечает, парсер опрашивает соседние узлы (`host + 1`, `host + 2`, `host - 1`), отдавая приоритет старшим серверам, куда чаще попадают новые товары.
    
- **Резервные ключи:** Парсер умеет извлекать данные из альтернативных полей JSON (например, поиск названия в `imt_name`, а при отсутствии — в `subj_name`).
    
- **Retry Missing:** Артикулы, не найденные с первого раза, помещаются в очередь на повторную обработку. Выполняется до трех дополнительных проходов с увеличенными интервалами (5 секунд) для обхода временных сетевых блокировок.
    
- **Заглушки:** Если товар недоступен глобально, скрипт генерирует строку со статусом «Не найден» и прямой ссылкой, сохраняя структуру выходного отчета.
    

## Стек технологий

- **Python 3.10+**
    
- **requests** (HTTP-запросы)
    
- **openpyxl** (генерация `.xlsx`)
    
- **gspread + google-auth** (интеграция с Google Sheets API)
    

## Установка

Bash

```
git clone https://github.com/<your-username>/wb-parser.git
cd wb-parser
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
# source .venv/bin/activate

pip install -r requirements.txt
```

## Настройка

Скопируйте шаблон конфигурации и укажите свои значения:

Bash

```
cp .env.example .env
```

Экспорт в Google Таблицы **необязателен**. Если ID таблицы не задан, будет создан только локальный Excel-файл. Для настройки экспорта в облако:

1. Создайте сервисный аккаунт в Google Cloud и скачайте JSON-ключ.
    
2. Сохраните ключ в корне проекта как `credentials.json`.
    
3. Откройте доступ к целевой Google Таблице для email-адреса сервисного аккаунта.
    
4. Укажите `WB_SPREADSHEET_ID` в файле `.env`.
    

## Использование

1. Поместите артикулы в колонку A файла `articles.xlsx` (по одному в строке, первая строка — заголовок).
    
2. Запустите парсер:
    

Bash

```
python wb_parser.py
```

Результаты сохраняются в файл `wb_results.xlsx`.

## Выходные данные

|**Колонка**|**Описание**|
|---|---|
|**Артикул**|Уникальный идентификатор товара|
|**Название**|Наименование|
|**Бренд**|Производитель / Торговая марка|
|**Цена (руб)**|Текущая цена со скидкой|
|**Цена без скидки**|Исходная цена|
|**Скидка %**|Фактический процент скидки|
|**Рейтинг**|Оценка покупателей|
|**Отзывы**|Общее количество отзывов|
|**Остаток**|Количество единиц на складах|
|**Дата обновления**|Время сбора данных|
|**Ссылка**|Прямой URL на карточку товара|

Принцип такой : даёшь ему Excel со списком артикулов — он по каждому лезет на серверы WB, вытаскивает карточку товара (название, бренд, цена, скидка, рейтинг, отзывы, остаток) и складывает всё в два места: локальный `wb_results.xlsx` и Google-таблицу клиента. Всё. Но Wb не отдаёт данные через один централизованный ip, они размазаны по двум механизмам. Прикол этого парсера в том, что он по сути дергает второй, когда первый не отвечает.

Работает так. WB хранит статичные карточки (картинки, описания, бренд) на CDN - это куча серверов с адресами `basket-01.wbbasket.ru`, `basket-02...` и так до `basket-25` и дальше. Какой именно сервер хранит конкретный товар - зависит от артикула. Берёшь артикул, делишь на 100000 - получаешь число `vol` . И вот по этому `vol` таблица говорит: vol до 143 лежат на сервере 1, до 287 - на сервере 2, и так далее. Дальше собирается URL вида `basket-05.wbbasket.ru/vol1234/part123456/12345678/info/ru/card.json` - и оттуда забирается JSON карточки

И второй источник - card.wb.ru . Это уже динамический апи , он отдаёт цену, скидку, рейтинг, остатки, которые меняется определённый промежуток времени. Поэтому код сначала обращается сюда ( тк тут всё актуальное), а если молчит - идёт к basket CDN


**Немного про fallback**

**1. Алгоритм поиска соседних серверов**
Про это я уже упоминал чуть ранее. Парсер вычисляет номер сервера (от 01 до 25) для статического хранилища по артикулу (параметр `vol`) через захардкоженную таблицу. Так как Wildberries периодически меняет границы распределения товаров в CDN, реализован fallback на соседние узлы: если по расчетному серверу данных нет, скрипт последовательно опрашивает `host + 1`, `host + 2` и `host - 1`. Смещение приоритета в сторону +1 и +2 связано с тем, что новые товары чаще попадают на старшие сервера

**2. Глобальное переключение источников (Card API → Basket CDN)** 
Про это тоже упоминал. Сначала к Card API, если ответа нет → Basket CDN

**3. Перебор регионов доставки**
Card API опрашивается не по одному URL, а через массив `CARD_ENDPOINTS`. В нем прописаны разные параметры `dest` (идентификаторы регионов доставки) и `appType`. Скрипт перебирает их до первого успешного ответа с кодом 200 и непустым списком товаров, компенсируя региональное отсутствие товара или сбой конкретного эндпоинта

**4. Пакетный повтор для потерянных артикулов (мега важно)**
Артикулы, по которым не удалось получить данные ни из одного источника, собираются во множество `missed`. Функция `retry_missing` делает до трех (`MAX_RETRIES = 3`) дополнительных проходов по этому списку с увеличенными паузами (`RETRY_DELAY = 5`) для восстановления после временных сетевых блокировок
 
**5. Резервные поля данных**
Внутри JSON-ответов предусмотрено чтение альтернативных ключей:
**Название:** в Basket CDN сначала ищется `imt_name`, при его отсутствии - `subj_name`
**Цена:** скрипт берет цену со скидкой (`salePriceU`), а если её нет - базовую (`priceU`)

**6. Заглушки для сохранения структуры** 
Ееесли после всех попыток товар не найден, функция `build_rows` создает для него статус "Не найден", сохраняя исходный артикул, дату и генерируя прямую ссылку. Это защита от нарушения изначального порядка строк из входного файла Excel при экспорте
